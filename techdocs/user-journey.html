User Journey: the app as it stands

What a person actually does in ECM JIRA Clone, from first sign-in to running sprints and writing docs. Every step below is taken from the routes, layouts and sidebar in the current code.

The product is now two apps behind one top bar: JIRA Lite (projects, backlog, boards, sprints, issues, reports) and Confluence Lite (spaces, wiki pages, documents). You switch between them with the app switcher. Each has its own sidebar (JL-153).

Personas

Workspace roles decide what the sidebar shows and which actions are enabled (usePermissions()). Project roles (Lead/Admin/Member/Viewer) narrow this further inside a project. Workspace Admins and Owners skip project-level checks.

Owner

Workspace owner

Everything an Admin can do. Owner is a flag (JL-317), not a role you can assign, so the Owner row has no role dropdown.

Admin

Workspace admin

Invites people, changes roles, manages Members and Users, and sets up workflows, custom fields, webhooks and approval rules.

Member

Team member

Creates and edits issues, comments, logs work and moves cards. Can see the Teams directory but not Members or Users.

Viewer

Read-only

Sees boards, issues and reports. Create, edit and delete controls are hidden or disabled.

Invitee

Not signed up yet

Arrives from an invitation email. The accept-invite page loads before the login gate, because this person has no account yet (JL-361).

Stages

1

Get in

LoginPage · /accept-invite · /reset-password
  1. A signed-out visitor gets the Log In / Sign Up tabs. You can switch tabs with the arrow keys (JL-264), and the browser tab title changes with the mode (JL-265).
  2. SSO buttons only show when the backend reports a configured SSO method (JL-129). Otherwise they stay hidden.
  3. Forgot password has three steps: enter email → enter token → done. The link in the email opens /reset-password, which loads ahead of the login gate (JL-370).
  4. An invitee clicks the link in the email, lands on /accept-invite, sets up the account and gets signed in. The inviter is told whether the email was actually sent (JL-473).
  5. A JWT is stored (localStorage or sessionStorage). After that, every API call sends it automatically.
Outcome: signed in. The app loads the dashboard, issues, sprints, members, projects and notifications in one batch.
2

First run with no projects

/projects
  1. With no project access, every project-scoped route (/, /backlog, /board, …) redirects to /projects.
  2. Sidebar items that need a project are greyed out with the tooltip "No project access". Teams, Members and Users stay usable.
  3. Someone with canCreateProject opens Create project, either from the page or from the + next to Projects in the sidebar, and picks Scrum or Kanban.
  4. The new project appears in the sidebar's expandable project list. Each entry links to that project's board.
Outcome: a project exists, and the rest of JIRA Lite unlocks.
3

Plan work

/projects/:id · /projects/:id/backlog

The project tabs are Summary · Backlog · Active sprints (only while a sprint is running, JL-460) · Reports · List · Settings.

  1. Summary gives the project overview, with quick-action buttons for Roadmap and Wiki (JL-456). Those buttons are now the only way to reach them from the project.
  2. Create issue: choose Epic, Story, Bug, Task or Sub-task, then set priority, assignee and description (rich text / markdown).
  3. In the Backlog, create a sprint and drag or assign issues into it.
  4. Bulk toolbar: select several rows and change Status, Assignee, Priority or Sprint, or Delete them after confirming (JL-39, JL-464).
  5. Flag an issue as an impediment. The flag button flags; it no longer changes status (JL-466).
  6. Import / Export from the Backlog toolbar: CSV/JSON export, and import with column mapping and a dry-run preview (JL-40).
Outcome: a groomed backlog and a sprint ready to start.
4

Run a sprint

/projects/:id/active-sprint · /projects/:id/board
  1. Start the sprint from the Backlog. The Active sprints tab appears.
  2. Move cards across Backlog → To Do → In Progress → Code Review → Done. Each status has its own label (JL-465).
  3. If an admin set an approval rule on a transition, the move waits for approval (JL-45).
  4. Automation rules can react to status changes and comments by assigning, transitioning, commenting or notifying. They are loop-safe (JL-38).
  5. A parent issue can't be closed while it still has open sub-tasks (409).
Outcome: work moves through the workflow and every move is recorded in activity history.
5

Work an issue

/browse/JL-63 (canonical) · /issues/:id
  1. Open an issue by its key. /browse/KEY is the canonical URL you can share, and the breadcrumb links work (JL-148/149).
  2. Edit the fields: status, assignee, priority, labels (colored chips with inline create), estimate (1d 4h, 45m) and custom fields under "More fields".
  3. Add child issues (shown with a progress bar), issue links (blocks / duplicates / relates to), attachments (up to 10 MB) and linked wiki pages.
  4. Use the activity tabs: All · Comments · History · Work log. Comments support @mentions with autocomplete, shown as chips.
  5. Watch the issue. You are added automatically when you create it or comment on it.
Outcome: one page holds the issue's full context, and you can share it by key.
6

Stay informed

Top bar bell · /activity
  1. The notification bell shows an unread count that updates live over SSE. You can mark items read one at a time or all at once.
  2. Notifications come from mentions, comments on watched issues and automation notify actions.
  3. On Profile, set preferences: in-app, email, and digest frequency.
  4. The Activity feed can be filtered by type, project, actor and date range, and scrolls infinitely.
7

Track & report

/dashboard · /reports · /filters · /list · /portfolio · /report-builder
  1. The Dashboard is the home page and has four widgets (JL-469–472).
  2. Reports per project. Status lists come from the server's validation vocabulary, so no issues are left out (JL-467).
  3. The List view shows a flat issue table, per project or across all projects.
  4. Filters are saved searches. Portfolio and Report Builder give cross-project views.
8

Document in Confluence Lite

/wiki/* · /spaces · /spaces/:spaceKey
  1. Switch apps with the app switcher. Confluence Lite has its own sidebar; no Jira chrome is shown (JL-153/155).
  2. The Home page lists recently modified pages. The sidebar also has Recent, Starred and Search (with excerpts and space filter).
  3. Spaces: create or delete a space from the sidebar (JL-156) and open it by key, e.g. /spaces/ENG (JL-162). A space doesn't have to belong to a project (JL-157).
  4. Pages: create one from a template, edit it, link to another page by title, and upload images in the editor (JL-99/101).
  5. Version history: compare and restore versions. Pages also have comments and attachments.
  6. Documents tab in a space: upload files (multipart, up to 100 MB, executables blocked), organise them in folders and see version history (JL-164–170).
  7. Link pages to JIRA issues in both directions. The page shows up on the issue too.
Outcome: project knowledge sits next to the issues it describes.
9

Administer

/teams · /members · /users · /workflow-editor · /audit-log · /projects/:id/settings
  1. Teams (/teams, anyone): the team directory, with a profile page per team at /teams/:teamId.
  2. Members (/members, Admin+): the member directory. Status filter defaults to Active, and an inline dropdown changes workspace role.
  3. Users (/users, Admin+): full user management. Invite, deactivate (a suspension that keeps role and history) or delete. Status pills: Active, Invited, Deactivated.
  4. Workflows: edit statuses and transitions. Audit log: see who changed what.
  5. Project settings: project details and members. Project roles are not edited inline here.
Guard railsThe server rejects removing the last Admin and changing the Owner, and the UI shows that rejection rather than enforcing the rule itself.

Built, but not in the launch sidebar

With LAUNCH_SIDEBAR = true (JL-277), the sidebar shows only: Projects, Teams, Members, Users, Filters, Activity, Workflows, Audit Log, Dashboards, Portfolio, Report Builder. The pages below still exist and open by URL, but there's no link to them in the sidebar:

AreaRoutes
Planning/roadmap, /advanced-roadmap, /releases, /goals
Service desk/queues, /incidents, /portal (Help Center), /knowledge-base, /assets
Integration/webhooks, /inbound-email, /automation, /bi-export, /marketplace, /plugins
Views/shared-dashboards, /cross-project-boards
Project wiki (legacy)/projects/:id/wiki, reachable from the Summary page's Wiki button

To show the full navigation, set LAUNCH_SIDEBAR to false in src/components/layout/Sidebar.jsx.

Known rough edges in the journey

Two admin member lists/members and /users overlap. Both are Admin-only member lists, and /users does more. Tracked as an open follow-up after JL-425.
Roadmap and Wiki tabs removedThe project top panel no longer has them, so the Summary page's quick-action buttons are the only in-app way in.
Two wikisThe older per-project wiki (/projects/:id/wiki, JL-48) and Confluence Lite (/wiki, /spaces) both exist. A new user may not know which one to use.
