1. Product overview ↑

1.1 What the system is

ECM JIRA Clone (package name jira, referred to internally as "jira-lite") is a self-hosted, multi-project agile work-management application. It reimplements the core of Atlassian Jira — issue tracking, Scrum and Kanban boards, sprints, workflows, reporting — and extends into adjacent Atlassian products: a Confluence-style project wiki, a Jira Service Management-style customer portal with queues, SLAs, incidents and an asset registry, and a Compass-style marketplace and plugin registry.

The architecture is a conventional two-tier web application:

  • Frontend — React 19 single-page application built with Vite, using Material UI v7 components over a CSS-custom-property layout system. State is held in seven React contexts; there is no Redux, no React Query and no client-side data cache beyond context state.
  • Backend — Express 5 REST API over PostgreSQL, accessed through the pg driver with a thin hand-written query layer. No ORM, no query builder, no migration framework.
  • Transport — JSON over HTTP with JWT bearer authentication, plus one Server-Sent Events endpoint (notification unread count) and one WebSocket hub (issue-detail presence and live updates).

The problem it solves is the standard one for the category: giving a software team a single place to record work items, order them into a backlog, commit them to time-boxed sprints, track them across a board, and report on throughput — without paying per-seat SaaS fees or sending project data to a third party. The distinguishing characteristic of this particular implementation is breadth over depth: it covers an unusually wide surface of Jira-family features, but many of those features are implemented to a demo or single-happy-path standard rather than to production completeness. That trade-off is documented feature by feature in Section 3 and collected in Section 8.

1.2 Who it is for

The system assumes a single organisation operating one workspace. A workspace is the tenancy boundary; the schema supports multiple workspaces and the API accepts an X-Workspace-Id header to select one, but the seeded default (slug = 'default') is what the application actually runs on, and several structural details — notably a globally unique projects.key and a sprints table with no project or workspace column — mean true multi-tenancy is not achievable at this commit.

Within that workspace the intended audiences are:

  • Delivery teams — engineers and QA working issues on boards, logging time, commenting, and running sprint ceremonies including retrospectives.
  • Team leads and project administrators — configuring boards, workflows, custom fields, sprints and project membership.
  • Programme and portfolio managers — using the portfolio view, advanced roadmap, goals/OKRs, releases and the report builder.
  • Workspace administrators — managing users, invitations, the signup deny-list, security policy, audit log, webhooks and integrations.
  • Requesters and customers — via the service-desk portal and knowledge base, though note that these are reachable only by authenticated users at this commit (see 3.10).

2. Personas, roles and permissions ↑

2.1 The two-tier model

Authorisation is organised into two independent tiers that are combined at evaluation time.

Tier 1 — workspace role. Every person has exactly one workspace-level role, stored in members.role with a separate boolean members.is_owner. The role vocabulary is Owner > Admin > Member > Viewer. This role applies across the whole workspace and governs administrative capability: user management, invitations, security policy, webhooks, audit log, workflow configuration.

Tier 2 — project role. A person may additionally hold a role on any individual project, stored in project_members.role, or be designated project lead via projects.lead_member_id. The vocabulary is Lead > Admin > Member > Viewer.

Both tiers share one numeric rank table, defined in server/middleware/authorize.js and mirrored in src/hooks/usePermissions.js:

Viewer: 1    Member: 2    Admin: 3    Lead: 4    Owner: 5

Note that project Lead outranks Admin in this table. The stated intent (comment at authorize.js:5) is that the project Lead is the highest project tier and therefore has full project-admin rights. The Owner: 5 entry was added defensively (JL-317) so that a member whose role column literally reads 'Owner' but whose is_owner flag is false does not fall to rank 0 — below Viewer — and get locked out of every role-gated route.

How the tiers interact

Three composition rules are applied, and it matters which one a given endpoint uses:

  1. Owner bypasses everything. requireRole() returns immediately if req.user.isOwner, without consulting rank at all.
  2. Workspace Admin and Owner bypass all project-level checks. requireProjectRole(), requireProjectRead() and requireProjectWrite() each short-circuit for isOwner || workspaceRole === 'Admin' before performing any database lookup. A workspace Admin therefore has full access to every project regardless of membership.
  3. Otherwise the higher of the two ranks wins. resolveProjectAccess() returns effectiveRank = max(workspaceRank, projectRank). A workspace Viewer who holds project Member on one project is treated as a Member on that project. This is the rule that makes it safe to default self-registered users to workspace Viewer.

Access for non-admins is membership-based and deny-by-default: resolveProjectAccess() grants hasAccess only when the caller has an explicit project_members row (any role) or is the project's lead_member_id.

One important asymmetry. requireProjectRead() deliberately allows the request through when the target project does not exist or cannot be resolved — for example an issue with a null project_id — so the handler can return its own 404 or legacy response. requireProjectWrite() in the same situation falls back to the legacy workspace-role gate (Member or above). Neither returns 403 for an unresolvable target. This is intentional backward compatibility for project-less data, but it means the guards are permissive at the edges.

2.3 Client-side capabilities

src/hooks/usePermissions.js is the single source of UI gating. It takes an optional projectId, reads the current member from MemberContext (populated by GET /api/auth/me, which returns workspaceRole, isOwner, projectRoles[] and projectCreationPolicy), and returns 21 capability booleans plus four metadata fields.

It fails closed: when currentMember is null — during load, or if the /me call fails — it returns loaded: false and every capability hard-set to false.

Declarative gating is available through src/components/auth/RequireRole.jsx, which accepts either a permission key (looked up on usePermissions) or a role name, and supports two modes: hide (render a fallback, the default) and disable (clone children with disabled, dim them, and wrap in a tooltip).

RequireRole carries its own local rank table { Viewer: 1, Member: 2, Admin: 3 } which omits Lead and Owner. A call of <RequireRole role="Lead"> resolves the required rank to 0 and therefore always passes. Only two routes in the whole application use RequireRole at the route level (/teams and /users, both by permission), so this has not yet caused a live defect — but the divergence from ROLE_RANK is a latent trap.

3. Functional modules ↑

3.1 Issues, sub-tasks and hierarchy

The issue is the central entity. Types are constrained by a live CHECK constraint to Epic, Story, Bug, Task, Sub-task. Issue keys are generated per project from a monotonic projects.issue_counter (JL-92), backfilled at boot from the maximum existing suffix.

Capabilities. Create, read, update, delete; status transition as a distinct endpoint; clone; bulk update; field history (issue_history, feeding cycle-time and CFD reports); watchers; votes; comments with emoji reactions; @mentions; attachments; links; worklogs; labels; components; custom field values; security level; flag.

Key endpoints. GET /api/issues (list with status, q free-text and jql parameters, scoped to accessible projects); GET|PATCH|DELETE /api/issues/:id; PATCH /api/issues/:id/status; POST /api/issues/:id/clone; POST /api/issues/bulk; GET /api/issues/:id/history; GET|POST /api/issues/:parentId/subtasks; GET /api/issues/:id/epic-children.

UI surfaces. IssueDetailPage (the largest interaction surface: description with rich-text editing, comments, worklog tab, attachments grid, links panel, child-issues panel with progress bar, labels picker, dynamic custom-field section, approvals panel, watchers, votes); CreateIssueModal; IssueListPage (saved list views, sorting, bulk actions); plus the board and backlog.

Hierarchy — three unrelated mechanisms

This is one of the more confusing areas of the product and worth stating precisely.

  1. issues.epic_id — self-referencing FK, ON DELETE SET NULL. Represents Epic → child. Validated by validateEpicRef: the target must exist and be of type Epic; an Epic may not have an epic_id; a Sub-task may not have an epic_id.
  2. issues.parent_id — self-referencing FK, ON DELETE CASCADE. Used only for Sub-tasks. POST /api/issues/:parentId/subtasks hardcodes the type to Sub-task, inherits project and sprint from the parent, and rejects a parent that itself has a parent_id. Closing a parent with open sub-tasks returns 409.
  3. The roadmap_epics table — a wholly separate table (id, name, phase, start_date, end_date, project_id) with no foreign key to issues at all. Exposed read-only by GET /api/roadmap; there is no create, update or delete endpoint.

A genuine three-level Epic → Story → Sub-task hierarchy is therefore only partially enforced. The rules that are enforced are the two listed above. What is not enforced: nothing prevents a Story from carrying both an epic_id and a parent_id; and because the sub-task check tests only "the parent has no parent", a Sub-task can be created directly beneath an Epic through the parent_id path — contradicting the epic_id rule that forbids the same relationship.

3.2 Boards, backlog, sprints

Board

src/pages/BoardPage/BoardPage.jsx. Drag-and-drop uses native HTML5 dragover/drop handlers, not a library. Columns come from board_configs (GET|PUT /api/projects/:projectId/board-config), each column mapping one or more statuses; when no config exists it falls back to the project's workflow statuses and then to a hardcoded default. A full in-page column editor supports add, rename, delete, reorder and status remapping.

Supporting features: swimlanes by none | assignee | epic | priority; quick-filter chips derived from current issues plus project labels (AND across categories, OR within a category), persisted per project in localStorage; an estimation statistic selector (story_points | time_estimate | issue_count); and column width persistence in localStorage.

WIP limits are advisory only. An over-limit column gains the CSS classes kanban-col-over-wip and kanban-count-over and displays count / limit, but the drop handler does not block the move. There is no server-side enforcement either.

Backlog

src/pages/BacklogPage/BacklogPage.jsx. Renders one collapsible panel per sprint plus a Backlog panel, with drag-and-drop between panels (dropping into Backlog clears sprint_id), inline per-panel quick-create, ranking arrows, and a search filter. The bulk toolbar supports status | sprint | delete | watch | unwatch applied over a checkbox selection, plus a multi-step BulkChangeWizard and the ImportExportModal.

Sprints

Sprint state is expressed by is_started plus the timestamps start_date, end_date and completed_at; there is no status enum. Endpoints under /api/sprints cover list, create, patch, start, complete and delete, all Admin-gated except the list. Starting a sprint snapshots committed scope into sprint_scope so burndown and burnup have a stable baseline, and fires a sprint.started webhook. Retrospectives (well | improve | action) and sprint templates are implemented in the same module.

ActiveSprintPage renders one board per active sprint and supports parallel sprints, gated by the per-project allow_parallel_sprints flag (JL-124).

The sprints table has no project_id column. Sprints are global to the installation; project association exists only transitively through issues.sprint_id. Consequences visible in behaviour: GET /api/projects/:id/sprints/active validates the project id but does not use it in the query, returning all globally active sprints; and the parallel-sprint guard counts active sprints across the entire installation rather than per project.

3.3 Roadmaps, releases and goals

Two roadmap pages exist and they are backed by entirely different data.

  • RoadmapPage reads GET /api/roadmap → the roadmap_epics table. Because that table has no link to issues, the page fabricates the hierarchy: a comment at RoadmapPage.jsx:111 reads "Map issues to epics heuristically (distribute across epics by index)", assigning issues[i] to epics[i % epics.length], and child bar dates are synthesised by slicing the epic's date range into equal slots. This page displays no real relationship data.
  • AdvancedRoadmapPage reads GET /api/advanced-roadmap, which selects real issues of type Epic across accessible projects and rolls up children through epic_id (child count, done count, points, percent done). It additionally supports roadmap_dependencies between epics with Admin-gated CRUD, team_capacity records, and computed dependency-violation and capacity-overload warnings. This is the functional roadmap.

Releases (releases table, status unreleased | released) support per-release issue lists, progress rollups, generated release notes, and fix/affects version association through issue_versions. Goals implement a lightweight OKR model: a goals row (status on_track | at_risk | off_track | done) with child key_results carrying target and current numeric values and an optional link to an issue.

3.4 Workflows and transitions

Workflow is modelled in three tables: issue_statuses (per project, or global when project_id is null, with a board category of todo | inprogress | done), workflow_transitions (per project, from_status → to_status with JSONB validators and post_functions), and project_workflows (per project metadata: initial status, terminal statuses, cancel-from-any behaviour). A legacy flat workflows table also exists and is served by GET /api/workflows as a static catalogue.

The engine is server/services/workflow.js. isTransitionAllowed() applies, in order:

  1. Same status → allowed (no-op).
  2. cancelFromAny is set and the target is the cancel status and the source is not terminal → allowed.
  3. Source is a terminal status → denied.
  4. The project has zero configured transitions → allow everything (explicit backward compatibility for pre-JL-79 projects).
  5. Otherwise, require a matching transition row.

Validators support one type, required_field. Post-functions support set_field and add_comment; settable fields are restricted to a whitelist (assignee, priority, resolution, environment, components) because the column name is interpolated into SQL. Post-functions write directly to the database and never re-enter the engine, so they cannot loop.

Templates. server/services/workflowTemplates.js exports exactly one template, QA Lifecycle (qa-lifecycle). See 6.1 for its full state and transition set. server/services/workflowSeed.js applies it idempotently and additively at boot to any project lacking a workflow (JL-334), never overwriting a configured one, and copying down global statuses first if the project has none of its own (JL-332).

UI. WorkflowEditorPage is a canvas editor with draggable status nodes and drag-to-create transitions (JL-324), a rules panel for validators and post-functions, and template application. Its limitations are covered in 8.1.5.

3.6 Search, JQL and filters

There are two separate, mutually incompatible JQL parsers in the codebase. They accept different field sets, different operators and different boolean connectives. Which one you get depends on which endpoint you call.

Parser A — server/services/jqlSearch.js, used by GET /api/issues?jql=

A regex scanner rather than a tokeniser: a single clause regex is run with exec() in a loop, ORDER BY is peeled off first, and the connective between two clauses is inferred by testing the intervening text for OR. Consequently NOT is not supported and there are no parentheses or operator precedence — clauses fold strictly left to right.

  • Fields (whitelist): status, priority, assignee, reporter, type/issuetype, project, key, title, created, updated, due, start. Notably absent: sprint, labels, epic, text.
  • Operators: =, !=, >, >=, <, <=, ~ (compiles to ILIKE '%v%'), IN, NOT IN. IS EMPTY is not supported. IN with a literal list is rejected — it requires a function value.
  • Functions: currentUser(), membersOf(role) and linkedIssues(key) (both DB-resolved and expanded into an IN list), plus the date functions now(), startOfDay(), endOfDay(), startOfWeek(), endOfWeek() and relative offsets such as -7d, +3d, -2w.
  • History operators (JL-118): field WAS value, field WAS IN (…), field CHANGED, compiled to a correlated EXISTS over issue_history against a second whitelist that does include sprint and epic.

Parser B — inline in server/routes/filters.js, used by POST /api/filters/jql

A smaller and differently-shaped parser. It splits on AND only, so OR is not supported at all. Its field map does include sprint and summary but excludes the date fields. It supports literal IN (…) lists and IS EMPTY / IS NOT EMPTY — both of which Parser A lacks — and multi-field ORDER BY, but no comparison operators and no functions whatsoever. This is the parser the frontend's filterApi.js calls.

Both parsers are safe from SQL injection. Column names are drawn exclusively from whitelist maps and every user-supplied value is bound as a parameter. jqlSearch.js carries an explicit "safety contract" comment block and dedicated tests. The one raw interpolation, ORDER BY ${order} in filters.js, is constructed only from whitelisted column names plus a forced ASC/DESC.

Natural-language search

POST /api/filters/ai-search is labelled AI in the UI but performs no model call of any kind. There is no LLM SDK in package.json and no outbound HTTP request in the handler. parseNaturalLanguage() is a set of hardcoded substring maps (status, priority, type), regexes for assignee and quoted text, and ordering hints, which return an interpreted array of human-readable strings that the UI presents as an explanation. Known weaknesses in the heuristic: "my issues" and "assigned to me" are explicitly not handled; the bare word "issue" maps to type Bug; and a bare "high"/"medium"/"low" anywhere in the string sets priority.

Saved filters (filters table with JSONB criteria, private or shared visibility) support favouriting via filter_favorites. Owner-only update and delete.

3.9 Automation, webhooks and integrations

Automation (server/services/automation.js + automation.js routes). Rules carry a trigger, an optional condition, an action, and an enabled flag, with per-execution logging to automation_logs. Triggers are status_changed, comment_added and scheduled; actions are assign, transition, comment and notify. Scheduler (server/services/scheduler.js). A single in-process setInterval, default 60 seconds, unref'd and guarded against double-start. Each tick runs due scheduled automation rules and then runs notification digests (piggybacked, JL-303). There is no cron library and no external job queue, so scheduled work is bound to a single process — which is why the pm2 configuration pins instances: 1.

Webhooks. Every endpoint is requireRole('Admin'). 4. Data model ↑

4.1 Access layer mechanics

The entire schema lives in one file, server/db.js (2,216 lines), containing 105 CREATE TABLE IF NOT EXISTS statements. There is no migrations directory and no migration framework.

  • Connection pool — pg.Pool with max: 10, 30 s idle timeout, 5 s connection timeout. An error handler logs unexpected idle-client failures rather than crashing.
  • convertPlaceholders(sql) — a SQLite-compatibility shim that rewrites ? to $1, $2, … left to right, tracking a naive in-string toggle so that ? inside single-quoted literals is skipped. Route files throughout the codebase still write ?; the conversion is transparent.
  • run() — auto-appends RETURNING id to any INSERT that lacks a RETURNING clause, and returns a SQLite-shaped { lastID, changes }. Tables without an id column must therefore supply their own RETURNING <col>; the codebase does this consistently for issue_labels, issue_components, issue_assets, issue_votes, scim_group_members and workspace_settings.
  • withTransaction(fn) — checks out one client, BEGIN, runs the callback with a transaction-bound {run, get, all}, then COMMIT or ROLLBACK. The transaction-bound run duplicates the RETURNING id logic verbatim rather than sharing it.
  • columnExists() / tableExists() — information_schema lookups that drive the whole migration strategy.

Migration approach

initializeDatabase() is not a versioned runner. It is a single idempotent "converge the schema" function executed on every boot, using four patterns: CREATE TABLE IF NOT EXISTS; guarded ALTER TABLE … ADD COLUMN behind a columnExists() check (with newer code using native ADD COLUMN IF NOT EXISTS); drop-then-re-add for CHECK constraints; and post-hoc foreign keys guarded by an information_schema lookup for cases where table creation order forbids an inline declaration.

Also embedded in the boot path are idempotent seeds (global priorities and statuses, default issue-type scheme, default permission and notification schemes, the singleton security policy, the default workspace) and data-repair migrations (legacy status colour remap, workspace-member healing, workflow de-duplication, issue-counter backfill).

A schema_migrations ledger table and a runMigration(version, name, fn) helper exist in server/services/migrations.js, but only a single 'baseline' row is ever written — the helper has no callers.

Two caveats worth noting. First, convertPlaceholders handles escaping only as sql[i-1] !== '\\'; it does not understand SQL-standard doubled-quote escapes (''), dollar-quoted strings, or -- and /* */ comments, so an apostrophe inside a comment would flip the in-string state for the remainder of the statement. Second, the SIGINT/SIGTERM handlers call pool.end() without awaiting it before process.exit(0), so in-flight queries are not drained on shutdown.

4.4 Referential integrity and delete behaviour

The delete-behaviour policy is consistent by intent: child and detail rows CASCADE, while classification references SET NULL (project, sprint, epic, release and security level on an issue; scheme on a project; workspace on a project or member). There is no RESTRICT anywhere in the schema — nothing blocks a delete.

Referential integrity is uneven. Roughly half the relationships in the system are real foreign keys; the rest are string joins on email or name with no constraint at all. issues.assignee, issues.reporter, comments.author, worklogs.author, watchers.user_email, workspace_members.member_email, filters.owner_email, saved_reports.owner_email, incidents.commander_email and oncall_shifts.user_email are all denormalised text. Renaming or deleting a person leaves dangling references throughout. user_audit_log.target_member_id is a deliberate exception — a bare integer so the audit row survives member deletion.

JSONB is used heavily as a schema escape hatch, across at least 22 columns including filters.criteria, shared_dashboards.layout, webhooks.events, board_configs.{wip_limits, quick_filters, columns}, workflow_transitions.{validators, post_functions}, issue_type_schemes.allowed_types, request_types.fields, assets.attributes, queues.filter, cross_project_boards.{project_ids, filter} and audit_log.metadata. Notably cross_project_boards.project_ids holds project references in JSONB with no enforcement.

Overlapping concepts

Several concepts are modelled twice, which is worth knowing before extending the schema:

  • issues.components (CSV text) vs components + issue_components.
  • roadmap_epics (standalone) vs issue_type = 'Epic' + issues.epic_id.
  • workflows (legacy flat) vs workflow_transitions + project_workflows + issue_statuses.
  • wiki_pages (internal, project-scoped) vs kb_articles (customer-facing, global).
  • member_capacity (per assignee per sprint) vs team_capacity (per team per period).
  • Four overlapping audit trails: activity, issue_history, user_audit_log and audit_log.

5. API surface ↑

5.1 Request pipeline

server/index.js asserts required environment variables and validates configuration before wiring anything, exiting non-zero on failure. Global middleware is applied in this order:

  1. requestLogger — correlation id and structured logging (JL-98).
  2. securityHeaders — CSP and related hardening (JL-91).
  3. corsAllowList — credentialed CORS; an empty allow-list is permissive, which is the development default (JL-93).
  4. ipAllowlist — no-op when unconfigured (JL-133).
  5. express.json({ limit: '25mb' }) with a verify hook that retains req.rawBody for webhook HMAC verification (JL-188).
  6. rateLimit on /api, with a second tighter limiter layered on /api/auth.

Authenticated routers are mounted behind a three-middleware chain:

const protect = [authGuard, loadUserRoles, resolveWorkspace]

authGuard verifies the JWT and sets req.user = { id, email }; loadUserRoles adds memberId, workspaceRole and isOwner; resolveWorkspace sets req.workspaceId from the X-Workspace-Id header or the default. resolveWorkspace is deliberately best-effort and never rejects a request.

After all routers, static serving is conditionally installed (see 7.5) and finally the shared errorHandler. On listen, the scheduler starts (skipped under test) and the WebSocket hub is attached to the HTTP server.

No role or workspace middleware is applied at mount time anywhere. Every mount is either public or app.use(path, ...protect, router). All role enforcement happens per-route inside the router files, which is why coverage varies so much between modules.

Transitions are evaluated by isTransitionAllowed() as described in 3.4. The most important behavioural consequence is rule 4: a project with no configured transitions permits every status change. Since backfillDefaultWorkflows() now seeds workflows at boot, newly created projects are constrained, but any project whose seeding failed (failures are logged and skipped so as not to block startup) silently reverts to permit-all.

6.2 Invitation, signup and the deny-list

Path A — token invitation

  1. An Admin calls POST /api/invitations with an email and one of Admin | Member | Viewer. A 409 is returned if the address is already a member.
  2. Any prior pending invitations for that address are revoked, so only the newest token is live.
  3. unblockSignup(email) is called — re-inviting a previously removed person is treated as explicit re-admission and lifts their deny-list entry.
  4. A 32-byte random token is generated with a 7-day expiry and a row is written to invitations with status pending. No members row is created yet.
  5. An email is sent fire-and-forget; the 201 response carries the raw token.
  6. GET /api/invitations/:token returns { email, role, status, expiresAt, expired, valid } for the accept screen.
  7. POST /api/invitations/:token/accept validates the token is pending and unexpired, then inside a transaction (JL-94) upserts the members row with the invited role and status Active and marks the invitation accepted. It creates a member, not a users login row — password setup still happens through signup.

Path B — direct member creation

POST /api/members, also Admin-only, writes a members row immediately with status Invited — or Active when a temporary password is supplied, in which case it also creates a users login row. There is no token, no expiry, no invitations row and no accept step. It validates the email more strictly than Path A, awaits the email send and returns its outcome, and writes a user_audit_log entry (Path A writes no audit entry at all).

Path C — self-signup redemption

POST /api/auth/signup opportunistically looks for a pending unexpired invitation matching the address, honours its role and marks it accepted — all inside a best-effort try/catch whose failure is swallowed. An invitation can therefore be redeemed without ever touching the accept endpoint.

The full signup sequence:

  1. Email format validation.
  2. checkSignupAllowed(email) — deliberately evaluated before any password rule, so a blocked or uninvited address gets a clear answer rather than being sent to fix a password for an account it could never create.
  3. Minimum length check, then the organisation password policy from security_policy.
  4. 409 if the email is already registered.
  5. Insert into users with a pbkdf2 hash (100,000 iterations, SHA-512).
  6. Member provisioning (best-effort, never blocks signup): the very first user ever created becomes workspace Owner with role Admin and is_owner = TRUE. Otherwise a pending invitation's role is honoured; with no invitation the default role is Viewer.
  7. Workspace bootstrap (best-effort): the first user becomes owner_email of the default workspace; every user is inserted into workspace_members.
  8. A 7-day JWT is issued and an auth.signup entry is written to the tamper-evident audit log.

The signup deny-list (JL-325)

Implemented in server/services/signupPolicy.js over the blocked_signups table (unique on LOWER(email)). Two independent controls exist, and the deny-list wins over the policy:

  1. The deny-list. Described in the source as "the offboarding guarantee": removing a member records their address here so that deleting a user actually revokes access, rather than being a formality they can undo by re-registering. Writes come from revokeAccessFor() on member removal; unblockSignup() is called when a member is re-added or re-invited. All writes are best-effort with errors swallowed, so deny-list bookkeeping never fails the delete that triggered it.
  2. The signup_policy workspace setting — open (the default, deliberately preserving historical behaviour so enabling the feature cannot lock a team out) or invite_only, which requires a pending unexpired invitation.

A blocked address attempting signup receives HTTP 403 with "This email address is not permitted to register. Contact your workspace admin." — before any password validation and regardless of the workspace policy. Admins manage the list through three requireRole('Admin') endpoints (GET, POST, DELETE /api/blocked-signups/:email), so blocks are visible and reversible without direct database access.

Two acknowledged holes in offboarding. First, revokeAccessFor() deletes session rows and deactivates the user, but authGuard verifies the JWT without re-reading user status — so an already-issued token keeps working until it expires (up to 7 days). This is noted in the source as tracked separately. Second, see the invite-email defect in 8.1.4.

6.3 Approval-gated transitions

The intended design: approval_rules declares that moving an issue from one status to another requires N approvals from holders of a given role; approvals records individual decisions; GET /api/approvals/check/:issueId?toStatus=X reports whether the gate is satisfied. Rule resolution is well done — a project-specific rule correctly wins over a global one via ORDER BY project_id DESC NULLS LAST LIMIT 1, and the check returns { required, rule, approvedCount, satisfied }.

As implemented, the approval gate is advisory and enforces nothing. Three independent findings:

  • Nothing consults it. approval_rules appears in exactly two server files: server/db.js and server/routes/approvals.js. Neither server/routes/issues.js nor server/services/workflow.js contains the string "approval". A status change is never blocked by an unsatisfied rule.
  • approver_role is never enforced. POST /api/approvals/issue/:issueId carries no requireRole middleware and never compares the caller's role to the rule's approver_role. Any authenticated user can record an approval or a rejection.
  • The frontend does not call the check either. src/api/approvalApi.js exports checkApproval(), but IssueDetailPage imports only fetchIssueApprovals and submitApproval. checkApproval is referenced only from test files. The UI is a sidebar panel listing recent decisions with ungated Approve and Reject buttons.

On rejection, nothing happens beyond the audit row and a notification to the assignee: no status revert, no reopen, no block. Because nothing consumes satisfied, there is no functional consequence.

7. Non-functional characteristics ↑

7.1 Authentication and session handling

  • JWT bearer tokens signed with JWT_SECRET, expiry controlled by JWT_EXPIRES_IN (default 7 days). authGuard verifies the signature and sets req.user; it does not re-check user status or session revocation on each request.
  • Password hashing is pbkdf2 with 100,000 iterations and SHA-512, stored as salt:hash.
  • Password policy is enforced from the singleton security_policy row at signup, change and login, including a maximum-age rotation check against users.password_changed_at.
  • Login lockout (server/middleware/loginLockout.js) throttles repeated failures. It is a process-wide singleton, which is why the auth route exports setLoginLockout() for test injection (JL-172).
  • MFA is TOTP-based and can be mandated workspace-wide by the security policy.
  • Client-side token storage is dual: localStorage when "remember me" is set, otherwise sessionStorage. getToken() reads both.

There is no 401 handling in the API client. src/api/client.js handles 403 by dispatching a global permission-denied event that surfaces a snackbar, but contains no 401 branch, and the string "401" does not appear anywhere in non-test frontend source. An expired or revoked token surfaces as a generic thrown Error: no automatic logout, no token clear, no redirect to login. The user sees repeated unexplained failures until they reload.

A second, smaller defect in the same file: unwrap() calls response.json() unconditionally on any ok response, with no branch for 204 or an empty body, so an endpoint returning no content throws a JSON parse error.

7.2 Database layer

PostgreSQL accessed through pg with a 10-connection pool. The compatibility shim described in 4.1 lets the entire codebase write ? placeholders while PostgreSQL receives $n. Every query in the audited routes binds user values as parameters; the only string interpolations found are column names drawn from closed whitelists (JQL ordering, workflow post-function target fields), each with an explicit comment explaining the constraint.

Schema convergence runs on every boot rather than through versioned migrations, which makes startup self-healing but means there is no down-migration path and no record of what changed when.

7.5 Deployment

Four production paths are checked in:

  • Dockerfile — genuine multi-stage: build stage runs npm ci and npm run build; runtime stage installs production dependencies only, sets NODE_ENV=production, SERVE_STATIC=1, copies dist/, and runs node server/index.js. Paired with docker-compose.prod.yml.
  • deploy.prod.sh — builds, rsyncs dist/ to the web root, restarts the API through systemd or pm2, and reloads nginx after a config test. This is what .github/workflows/deploy.yml actually invokes.
  • deploy/ — nginx site config, a systemd unit, and setup documentation; plus ecosystem.config.cjs for pm2, pinned to instances: 1 because the realtime hub and the scheduler are both in-process singletons.

7.6 Observability and hardening

  • Structured logging with a per-request correlation id (requestLogger, server/services/logger.js).
  • Health endpoints /api/health and /api/ready, unauthenticated by design.
  • Security headers including CSP; a CORS allow-list; an optional IP allow-list; and two tiers of rate limiting.
  • Email delivery log (email_log) recording recipient, type, status and error, so an invitation that never arrived can be distinguished from one never sent (JL-323).
  • Tamper-evident audit log. Each entry's hash is SHA-256 over a canonical pipe-joined string of sequence, actor, action, target, canonicalised metadata (recursive key-sorted JSON so insertion order cannot change the hash), previous hash and timestamp. Entries chain by prev_hash from a genesis of 64 zeros. verifyChain() walks entries in sequence order, checking both the stored link and the recomputed hash, and reports the sequence number of the first failure. Retention purges old entries and records a checkpoint (audit_checkpoint) holding the last purged sequence and hash, so the surviving chain still verifies while an unrecorded deletion is still detected. safeAppendAudit() swallows errors so audit logging can never break the action it records.

The audit chain's append path reads the highest sequence and then inserts, without a transaction. Concurrent appends can race on seq; the unique index on audit_log.seq will reject the loser rather than corrupt the chain, but the entry is then lost because safeAppendAudit swallows the error.

1 "Theme config in src/theme/muiTheme.js with light/dark variants matching Atlassian design tokens." The file and the whole src/theme/ directory do not exist. A repository-wide search for muiTheme returns nothing. Theme state lives in src/context/ThemeContext.jsx — 28 lines that store 'light' | 'dark' in localStorage['jira_theme'] and toggle a class on the document element. Styling is CSS-custom-property driven via src/styles/variables.css and theme.css.
2 "MUI ThemeProvider integrated in ThemeContext.jsx"; the provider list shows "ThemeContext (+ MUI ThemeProvider)". There is no MUI ThemeProvider anywhere in src/, and no createTheme call. MUI components are used with their default theme. This is a separate error from #1.
3 "Component: src/components/RequireRole.jsx" The real path is src/components/auth/RequireRole.jsx. The stated path does not exist.
4 "Key pages: Dashboard, Board, Backlog, ProjectSummary, ActiveSprint, Reports, Roadmap, Teams, Filters, Profile, ProjectSettings, WorkflowEditor, ActivityFeed, WikiPage, WebhooksPage, SharedDashboardsPage, AutomationPage." Substantially incomplete: there are 40 page directories. Entirely unmentioned are UserManagement, AuditLog, Portfolio, ReportBuilder, AdvancedRoadmap, Goals, Releases, Queues, Incidents, Assets, KnowledgeBase, Portal, Marketplace, Plugins, BiExport, InboundEmail, CrossProjectBoard, ProjectDetail, List and NotFound.
5 Lists 18 API modules by name. There are 58 modules in src/api/. Roughly two thirds of the client layer is undocumented.
6 "RESTful API under /api/ — auth, issues, sprints, projects, dashboard, reports, roadmap, workflows, members, profile, activity, comments, filters, notifications, watchers, approvals, shared-dashboards, webhooks, wiki" plus seven "Theme-1 routers". There are 74 route modules. Whole subsystems are unmentioned: SCIM, SSO/OIDC/SAML, MFA, API tokens, sessions, audit log, security policy, blocked signups, invitations, workspaces, permission and notification schemes, screen schemes, field configuration, issue-type schemes, security levels, SLA, queues, portal, incidents, assets, knowledge base, marketplace, plugins, git integration, CI/CD, BI export, inbound email, public API, health and docs.
7 Lists the collaboration and core-PM tables — roughly 25 across two sections. There are 105 tables in server/db.js.
8 "statuses (Backlog → To Do → In Progress → Code Review → Done)" Stale. ISSUE_STATUSES now holds nine values including In Testing, In Rework, In UAT and Cancelled (JL-306), and the seeded QA Lifecycle workflow does not contain Code Review at all.
9 "Schema in server/db.js with initializeDatabase()" and the CHECK constraint on issue_type. Correct as far as it goes, but omits that the status and priority CHECK constraints were dropped (JL-78) and moved to route-layer validation — a material change for anyone reasoning about data integrity.
10 "collaboration-modules.test.js (39 tests) … collaboration-enhancements.test.js (19 tests)" Describes two files out of 264. The testing section gives no indication of the suite's actual size, of the three distinct strategies in use, or that the suite does not currently pass clean.
11 "Approval Workflows (JL-45): approval_rules define required approvals per status transition… Check endpoint verifies if transition is gated." Technically accurate about what exists, but omits that nothing enforces it — no caller, no role check, no frontend usage. Reads as a working feature; it is not.
12 "Deployment (JL-97) … Dockerfile is multi-stage…" Accurate, but omits both deploy.sh and deploy.prod.sh entirely — the two scripts that actually deploy the system, and the source of the JL-326 debt.
13 "State management: React Context API — 7 nested providers" Verified correct — exactly seven providers (Auth, Theme, Issue, Sprint, AppData, Member, Notification), in the stated order, wrapped by a non-provider ErrorBoundary. Recorded here because it was the claim most likely to have drifted.

The general pattern is that CLAUDE.md accurately describes the system as it stood around the JL-31 to JL-48 work and has not been updated for the very large body of work since — identity and security (JL-73 onward), the two-tier project authorisation model (JL-224–226), the service-desk and ITSM subsystems, or the workflow-template rework (JL-306, JL-324, JL-331–334). It should be treated as a historical snapshot rather than a current map.
